## Hydration analysis

Per-component analysis of server/client render behavior:

| Component | `"use client"` in flowbite-react source? | Used in server component? | Hydration risk |
| --- | --- | --- | --- |
| **Navbar** (Header) | YES — `node_modules/flowbite-react/lib/esm/components/Navbar/Navbar.js` line 1 | YES — `components/Header/Header.tsx` has no "use client", rendered in `app/layout.tsx` server component | **Low.** Flowbite marks Navbar "use client" itself, so Next.js treats it as a client component boundary even when imported into a server component. Navbar uses `useState` for mobile collapse toggle — expected client behavior. Server renders initial HTML (expanded state); client hydrates and adds interactivity. No mismatch because initial server render matches default `open=false` state. E2e confirms no console errors. |
| **Card** (ArticleTeaser, ProjectTeaser) | NO — `Card.js` has no "use client" directive | YES — both teasers are server components | **None.** Card is a pure presentational wrapper (div + className). No state, no effects, no browser-only APIs. Renders identically on server and client. |
| **Alert** (contact form) | NO — `Alert.js` has no "use client" directive | Used in `app/contact/page.tsx` which IS "use client" | **None.** Alert renders conditionally (`showConfirmation && <Alert>`) inside an already-client component. Flowbite Alert's `onDismiss` prop is client-only but only fires on click. Server render omits the Alert (showConfirmation defaults false); client renders it only after submit. No mismatch. |
| **Tooltip** (ProjectTeaser) | NO — `Tooltip.js` has no "use client" directive | YES — ProjectTeaser is a server component | **Low.** Flowbite Tooltip internally uses `Floating` component which DOES have "use client" (`Floating.js`). Tooltip positions via Popper.js on client. Server renders trigger element; client adds floating content on hover. No mismatch because floating content is not in initial server HTML. E2e confirms no console errors on homepage projects marquee. |
| **Breadcrumb** (blog + project detail) | NO — `Breadcrumb.js` has no "use client" directive | YES — both detail pages are server components | **None.** Breadcrumb is pure presentational (nav + links). No state, no effects. Renders identically server and client. E2e breadcrumb navigation tests pass. |
| **NavbarToggle / NavbarCollapse / NavbarLink / NavbarBrand** | Navbar sub-components — NavbarCollapse, NavbarLink, NavbarBrand, NavbarToggle all carry "use client" | All used within Header (server) | **Low.** Same as Navbar — client boundary is respected. |

**Flowbite `theme-store`**: Tooltip, Breadcrumb, Card, and others import `getTheme` from `../../theme-store`. This is a module-level singleton initialized at import time. In App Router, server and client have separate module graphs, so the theme store is instantiated once per environment — no cross-boundary state leak. No hydration issue observed.

**No `"use client"` wrapper needed**: Flowbite-react v0.7.8 self-marks interactive components (Navbar, Dropdown, Modal, etc.) with `"use client"` at the source level. Components like Card, Alert, Breadcrumb, Tooltip do not need wrapping — they either are pure or delegate client-only behavior to internal client subcomponents (Floating). This is the correct App Router pattern.

## Strict mode conflicts

- React 18 strict mode double-renders in dev. Flowbite components use `useState` (Navbar, Tooltip/Floating) — double-render does not cause mismatches because:
  1. Pure components (Card, Alert, Breadcrumb) have no state — double render is a no-op.
  2. Stateful components (Navbar, Floating) use `useState` with deterministic initial values — double render produces the same output.
- No `useEffect` cleanup issues observed in e2e (which runs against dev server with strict mode behavior).
- **Verdict: no strict mode conflicts detected**

## Decision: KEEP

**Keep Flowbite at current version (v0.7.8 / flowbite ^2.2.0).**

### Rationale

The audit threshold from the plan defines "minor" as: no hydration errors, ≤2 console warnings, components render in App Router → keep Flowbite, document workarounds.

Actual findings:
1. **Hydration errors**: **0** — no hydration mismatches. Flowbite self-marks interactive components with `"use client"`, creating correct client boundaries. Pure components (Card, Alert, Breadcrumb) render identically server and client.
2. **Console warnings/errors at runtime**: **0** — Playwright e2e (7/7 pass) collects `console.error` messages and asserts none unexpected. All pass. Zero Flowbite-related console output.
3. **Build warnings**: **0** — `pnpm build` exits 0, zero matches for hydration/flowbite/warn/error in build log.
4. **App Router compatibility**: All 6 Flowbite-using files render correctly. 5 are server components, 1 is client (`app/contact/page.tsx` — client by necessity of `useState` + form handler, not because Flowbite forced it). No `"use client"` wrappers needed — Flowbite handles the boundary internally.
5. **Strict mode**: No conflicts detected.

All thresholds met for "minor" classification. No workarounds needed beyond Flowbite's built-in `"use client"` directives.

### Not upgraded because
- No symptoms warrant an upgrade. v0.7.8 is compatible with Next.js 14 App Router, React 18, and static export.
- Upgrading to v0.8+ would introduce API changes (Flowbite v0.8 changed theme customization API and component props) requiring a migration effort disproportionate to the zero observed issues.
- Risk of regression vs. zero benefit at this time.
